# NorthStar｜10 分钟 QA 备答

> 这 10 分钟用于互动，不是另一段演讲。每次先给 20–30 秒直接回答；有追问再扩展到 60–90 秒。以下是建议回答与备选材料，不能把验证计划说成已取得的成绩。

## 时间与回答方式

建议准备 6 个主问题：每题约 60 秒回答、30 秒追问，共 9 分钟；最后留 1 分钟给补充。实际由评委的问题决定，不 需要按序背完。

回答顺序：**先给结论 → 用一个产品例子说明 → 交代已完成和待验证的部分。**技术问题先解释它服务的用户任务，再补实现细节。

## 1．为什么要做？普通聊天工具和平台后台不能解决吗？

**30 秒回答**

我关注的是有稳定内容产出、同时做短视频和直播，但整理时间有限的创作者。平台后台提供数据，通用聊天工具提供生成能力；我的设计把账号资料、当前页面、产物保存和内容排期接起来，减少反复搬运。核心价值要通过同一任务的完成时间和产物采纳来验证。

**被追问：差异化在哪里？**

例如用户打开一份直播稿，助手应该知道当前稿件；用户问成交变化，应该引用对应场次和统计口径；生成结果确认后，能保存到指定知识库和排期。差异化在于持续的工作上下文和可执行流程。模型本身不是我的壁垒，长期优势还要靠可靠的数据接入、账号经验积累与高频使用形成。

**被追问：你访谈这么少，能说明市场吗？**

目前访谈帮助我提出需求假设，不能证明整个市场规模。我会先在教育类创作者中验证，因为我有自己的运营经验和课程资料；再扩大到其他垂类，观察需求是否仍然成立。

## 2．你自己做了什么？为什么作出这些产品选择？

**30 秒回答**

我主要负责用户需求梳理、场景与信息架构、任务链路、交互取舍，以及用真实资料验收和迭代。开发中使用了 AI 编程工具，所以我会区分产品决策、我推动完成的实现和工具辅助生成的代码。我的重点是把用户问题变成可验证的操作，而不是只做一个界面。

**60 秒扩展**

三个关键取舍：第一，首页结论前置，减少用户找重点的负担；第二，知识与回答可追溯，让生成有账号依据；第三，结果能入库和排期，让对话后续有动作。上线测试也发现了来源跳转、保存弹窗、任务与页面同步等问题，说明链路验收必须检查实际写入，不能只看模型回答成功。

**被追问：AI 工具做了大部分代码，如何体现能力？**

我会展示需求到实现的验收标准：引用必须打开正确文档，排期必须有正确标题、类型和时间，当前脚本必须完整进入上下文。工具能生成代码，但这些业务约束、优先级和验收判断需要我负责。没有亲自深入掌握的底层细节，我不会说成完全独立开发。

## 3．技术架构是什么？Agent 到底做了什么？

**30 秒回答**

当前采用 Vue 与 Vite 前端、FastAPI 后端和 SQLite 存储，部署在腾讯云。Cue 先识别任务，收集页面上下文和引用资料，再走数据查询、资料检索或模型生成，最后把结果接到保存和排期。它是规则路由与模型能力结合的任务流程。

**60 秒扩展**

数据问题优先通过结构化数据计算；资料问题检索文档片段；创作问题结合课程、脚本与页面上下文生成。前端负责会话和任务交互，后端负责认证、资料、数据与模型调用。当前没有多智能体自主协商系统，也没有完善的持续自动任务执行器。这样的实现先验证业务链路，后续再按需求增加复杂度。

**被追问：为什么不用多 Agent？**

当前高频任务的流程相对明确，先用可控的路由更容易验收来源、口径和写入结果。如果后续任务涉及并行调研、独立分析和审核，我才会评估多 Agent 的收益，同时测延迟、成本和一致性。

**被追问：为什么是 SQLite？**

它适合当前原型的规模和部署复杂度。若进入多用户高并发、复杂权限和持续采集阶段，需要根据负载迁移数据库、增加任务队列与监控。当前没有把原型说成已经具备大规模服务能力。

## 4．知识库、实体和图谱如何让回答更准确？

**30 秒回答**

首先要让正文提取成功，并能定位来源；其次通过分类和明确引用缩小范围；再把账号特有的方法整理出来。当前回答主要检索文档片段，图谱用于组织和查看证据，还没有直接驱动图检索。因此我不会仅凭展示图谱就说准确率提高了。

**60 秒扩展**

上传后提取正文与切分片段，AI 解析另行整理摘要、实体和概念。当前检索主要基于关键词与中文片段匹配，不是已经完成的向量或图 RAG。显式 @ 文档帮助锁定范围，课程概念保留原文解释，降低模型凭名字猜测的风险。下一步用标注问题集测试召回是否找到正确片段、回答是否忠于证据。

**被追问：上传了为什么有时还回答不了？**

文件存在，不等于正文已成功提取；正文存在，也不等于检索和权限正确。应分别检查提取状态、片段内容、引用文档 ID、检索范围和模型输入。产品需要让这些状态可见，并提供重新解析或补充资料入口，不能用一句“没有相关资料”把问题都推给用户。

**被追问：什么情况下图谱才值得做？**

当同一方法有多个别名、不同课程反复引用同一概念时，关系组织有价值。是否进一步用于召回，要与关键词、向量或混合检索做比较，评估命中率和成本，而不是为展示技术复杂度增加一层。

## 5．如何保证可信？示例这么快，是不是预设答案？

**30 秒回答**

部分固定示例使用提前整理并核验的答案，帮助高频问题快速返回；自由输入和复杂改写仍需实时处理。缓存应该保留来源、适用范围与更新信息，也不应把本轮没有发生的模型调用显示成已经发生。可信度取决于证据和结果，而不只是生成方式。

**被追问：那这次展示证明了什么？**

它证明了典型任务的呈现、引用、保存和排期链路可以被演示。它不能单独证明任意新问题都有相同质量。后续需要使用未预先准备的问题、不同资料和异常情况测试泛化能力，并分别报告缓存命中和实时生成表现。

**被追问：100ms 后兜底合理吗？**

100ms 可以作为缓存查找或返回策略的内部预算，但不能保证包含网络的全链路响应，也很难让完整模型生成在这个时间内完成。适合缓存的问题应优先命中；没命中再走实时流程。只有存在适用且未过期的结果时才兜底，不能为了速度返回不相关答案。

**被追问：思考过程是真的吗？**

这里应该展示可核对的任务步骤，例如确定范围、查找资料和组织结果；不是模型隐含思维链。缓存结果应说明沿用此前整理，实时流程记录真实发生的步骤，不能用虚构步骤证明可靠性。

**被追问：如何防止幻觉和错误归因？**

数字尽量通过结构化数据计算，附时间范围和口径；引用回到原文；事实和建议分开；关键高点只作为回看线索，不直接宣称因果。保存与排期还要检查实际写入。对于缺证据的部分，说明缺失并让用户补充。

## 6．怎么衡量价值？商业化和下一步怎么做？

**30 秒回答**

先验证它是否减少重复整理，再验证用户是否愿意持续使用。我会看同类任务的完成时间、脚本采纳率、入库与排期成功率，以及知识是否被再次引用。粉丝和成交是更远的结果，需要真实发布后的对照验证，目前不宣称已经提升。

**60 秒扩展：验证方法**

让同一类用户完成相近任务，比较原工作方式和使用 NorthStar 的时间与结果质量，避免只问主观满意度。记录每一步：检索、生成、修改、保存和排期。若时间减少但修改成本很高，仍不能算成功。再观察至少一个完整创作周期，确认是否真的复用知识并执行计划。

**被追问：北极星指标是什么？**

我建议先用“每周被用户确认并进入排期的有效内容任务数”作为候选指标；同时看后续执行率、满意度和错误率，避免靠重复写入抬高数字。这是待验证的指标设计，不是已经获得的统计结论。

**被追问：怎么赚钱？**

先验证教育类个人创作者和小团队的付费意愿，再测试按席位或按使用额度的订阅方式。价格需要结合节省时间、任务频率和模型成本确定，目前不报未经验证的定价或收入预测。

**被追问：下一阶段先做什么？**

先把资料提取、引用定位、保存与排期的稳定性做扎实，再验证跨周期复用。持续竞品采集、自动视频分析和更复杂 Agent 的优先级，应由真实使用频率与收益决定。

## 其他高频追问

| 问题 | 可以直接说的回答 |
|---|---|
| 数据从哪里来？ | 当前主要是上传资料、已导入的历史报表与内容材料，部分页面使用演示样本；公开竞品分析提供外部来源。不同来源要分别标识，不说成全平台实时数据。 |
| 竞品已经自动抓取了吗？ | 已有监控与候选加入流程；持续定时采集和自动发现还需要接入验证。今天不把已有列表说成实时全网扫描。 |
| 直播已自动全量分析了吗？ | 当前展示已导入的关键画面和复盘材料；部分媒体工具可以做提取，但不意味着每场都有完整转写、精确对齐和自动归因。 |
| 多轮对话是否永远记住？ | 可以围绕当前会话继续修改；并不意味着无限保留全部原文。需要关注上下文长度、引用保留与关键产物持久化。 |
| 云端和本地一定完全一致吗？ | 相同代码与资料是基础，还要核对账号、数据库、文件权限和运行配置。固定示例可以统一，自由生成不能保证逐字一致。 |
| 隐私和权限如何处理？ | 当前有登录和用户资料范围控制。正式商用还需系统验证隔离、日志、备份与删除机制，并明确模型服务的数据处理约定；不宣称已完成合规认证。 |
| 模型成本多少？ | 当前没有完整的线上成本测算。会按任务记录 token、调用次数、缓存命中和重试，再算每个成功任务的成本。不能只报一次调用的价格。 |
| 缓存会过期吗？ | 必须随资料版本与账号上下文失效或重算，特别是经营数字。目前还需要完善这套机制；不能把静态答案当长期可靠的数据查询。 |
| 模型失败怎么办？ | 已有适用结果时提供有标识的兜底；否则保留问题并支持重试。任务写入要避免重复，不能用“成功”的文案掩盖失败。 |
| 会自动发布吗？ | 当前重点是生成、确认、保存和排期，不是自动发布。发布后的结果接入与完整复盘循环仍需继续完善。 |

## 应对质疑的表达

**“这不就是套壳？”**

“模型调用只是其中一环。我希望证明的是资料、任务上下文和后续执行可以连起来。这个价值需要用任务耗时和采纳率验证，不能只靠界面或模型数量证明。”

**“现在还只是 Demo？”**

“它目前是可操作的原型，已经可以测试若干端到端流程，但还没有验证规模化运营和增长效果。我会把已经跑通的链路和下一阶段能力明确区分。”

**“你怎么知道这段话术带来了成交？”**

“目前只能确认它出现在该节点附近，是值得回看的线索。要判断影响，需要结合流量、商品和时间，并在后续场次重复验证。”

**“这个技术细节你不清楚？”**

“这一部分我还没有充分验证，我不先给未经核实的结论。我的验收重点是【对应任务结果】；后续我会通过【具体检查或测试】确认。”

## 答问前的事实边界速记

- 能展示：工作台、知识资料、可追溯引用、部分任务生成、多轮修改、确认入库、内容排期、已导入复盘和竞品对比。
- 不能直接声称：真实增长已经提升、所有文件均自动完成 AI 整理、图谱已提升召回、无人值守全网竞品监控、每场全量视频归因、每次回答均实时调用模型、生产系统零失败。
- 不报未测数据：准确率、节省比例、付费转化、月收入、单位用户成本。
- 演示中的历史报表、样本内容与未来计划使用不同时间口径；不为了衔接演示把它们说成同一实时周期。
